# Chat sessions

Claude and Codex chat sessions: drivers, profiles, slash commands, approval policy, question auto-answer, activity, background tasks, usage bar, notices, header, transcript, history window, drafts, search, archive, navigator. Part of [the architecture reference](README.md).

- Notification sounds: the Permission sound plays for any known session entering `permission`; the Idle sound plays on `working` -> `waiting`, except for the selected session while the page is visible and no Team page is open (the chat the user is actually watching). Both rules live in the pure `decideTransitionSounds` (`src/client/utils/soundTransitions.ts`), applied by the `sessions` and `session-update` handlers in `src/client/protocol/sessionMessages.ts`.
- Chat sessions use the Claude Agent SDK without tmux, driving a separately installed Claude Code executable (`KAWAI_CLAUDE_PATH` or `claude` on the server PATH; version-checked against the SDK-pinned baseline 2.1.289 before creation — the SDK's platform CLI packages are stubbed out of the install, so Claude Code must be installed on the host). Turns and pending approvals/questions determine status directly. WebSocket snapshots restore history and pending requests on reconnect; SQLite rows and SDK transcripts allow restart/resume.
- Codex chats (`codex-chat-sessions`) run the OpenAI Codex app-server instead of the Claude Agent SDK: a profile with `runtime: "codex"` (its `codexHome` and `network` are trusted-tier profile facts, accepted only from the user-level catalogs) and both are fixed at creation in `chat_sessions`; the executable comes from `KAWAI_CODEX_PATH` or the server PATH's `codex` and is version-checked against the 0.163.0 baseline (an older one refuses creation), and the resolved home must hold a usable login or creation refuses ("Codex profile "<label>" has no usable login in its Codex home. Sign in with `codex login` (ChatGPT plan or API key), then retry."). One `workspace-write` sandbox serves every Codex chat (writable root: the git common dir; network per the profile). Threads run `approvalPolicy: "on-request"` with `approvalsReviewer: "user"`, so every escalation Codex raises reaches Kawai and Kawai decides: under `manual` it shows its own approval cards (command, file-change, permission) and question cards (`isOther` gates the free-text input on a question with options — no options always offers text; `isSecret` masks the input, answered card included), under `auto` it accepts; commands inside the sandbox never escalate, so a manual Codex chat asks less than a manual Claude chat (accepted), and dynamic team-tool calls bypass Codex approval — never a card under either policy. The team tools register as one `kawai-team` dynamic-tool namespace at thread start, from the same `teamToolTable` the Claude MCP server renders (a test holds the two to one table); an `item/tool/call` runs only for the session's own thread — a child thread's call is refused, one carrying the session's thread id (as a subagent's carries its parent's) is served as the session — and only for the namespace, a tool in the table, and arguments its Zod schema accepts; every refusal and a throwing handler answer `success: false` text, never a JSON-RPC error and never a card. A thread resumed from before this change stored no tools, so group mail pushed to it cannot be answered — create a new Codex chat. The thread's transcript is its rollout file (`transcript_path`, `sessions/YYYY/MM/DD/rollout-<ts>-<thread>.jsonl`): mail receipts read `transcript_path` plus every `rollout-*-<threadId>.jsonl` under `<codex_home>/sessions` (a bounded depth-4 walk, never through a symlink), absence requeues only when the reader is proven and the path is named for the thread (otherwise the mail holds), history replay reads the rollout alone for live and archived chats alike (row ids derive from the line's index and content, so a rewritten row reads stale, and an unreadable rollout shows a history-unavailable notice that a later load retries while no live turn could be duplicated), and the log matcher excludes a chat's rollout from terminal-session parsing by `session_meta` id or file name.
- Chat profiles come from layered `providers.json`/`profiles.json` catalogs (`docs/claude-session-profiles.md`): the shipped `config/*.default.json` and user-level `~/.kawai/` files are trusted, project `.kawai/` files are not. Catalogs never hold credential values; a trusted provider may only name its key variables (`authTokenEnv` for inference, `balanceKeyEnv` for the server-only account key; the shipped `openrouter` names `OPENROUTER_API_KEY` and `OPENROUTER_MANAGEMENT_KEY`) — rejected in project files and any `profiles.json`, and a project file that redirects a credentialed provider's base URL or re-homes its model is rejected whole (openrouter-provider D1–D2). Every named variable is withheld from every agent launch; a credentialed session gets `ANTHROPIC_AUTH_TOKEN` from its variable with `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` blanked in the env and the flag settings layer, needs that variable to be created whatever host login exists ("Provider <label> needs <VAR> in the server environment."), and shows no login-expiry notice (D3–D4). Resolution is memoized once for the whole server (`catalogMemo.ts`, catalog-resolution-cache D1–D2): `providerOf`, `providerLabelOf`, and `providerDefinitionOf` read one LRU memo (64 entries) keyed by `catalogInputKey` — HOME, CODEX_HOME, the shipped default paths, and each existing level file with its kind, trust, tier, mtime, and size — so every project path that sees the same files shares one resolution, and an edit, a new file, or a deleted one changes the key and applies at the next lookup. `runtimeFactsOf` and the balance-key read use the same memo. `withCatalogSnapshot` holds the catalog still for one synchronous read, so each distinct context computes its key once; the mailbox's recipient sweep runs in one, and an edit applies at the first lookup after it (D3). Reset time-zone validity is memoized per zone string (256 entries).
- The chat agent starts when a client attaches (no prompt sent), so its slash-command list is ready before the first message; archived chats and sessions with a missing project directory start nothing.
- Slash commands: the agent-reported list (name, description, argument hint, aliases, project/user source; terminal-bound and internal commands hidden) rides in the chat snapshot and as `chat-commands` pushes with loading/ready/unavailable state. The composer's `/` menu opens for the `/` word at the caret anywhere in the message, filters and inserts commands in place without sending; local command output (`/context` etc.) renders in the transcript, and replayed history shows slash-command turns as typed with their output.
- `/clear`, `/reset`, and `/new [name]` never reach the agent: the client creates a new chat in the same project with the same profile and the same approval policy (named when given), selects it, then archives the previous chat; on creation error the current chat is untouched.
- Each chat session has a per-session approval policy (`approval_policy` in `chat_sessions`: `manual`, or `auto`): auto grants tool approvals without cards — AskUserQuestion still asks, and Claude Code settings deny rules still apply. New chats start with the client Settings default (`defaultApprovalPolicy`, `manual` unless saved as `auto`), sent as the optional `approvalPolicy` on `session-create` and overridable per session in the New Session dialog; the server falls back to `manual` when the field is absent. A chat created by `/clear`, `/reset`, or `/new` carries the previous chat's policy over instead of re-reading the default. Toggled live from the chat header's **Auto-approve** switch (`chat-set-approval-policy`); persisted across restart, resume, archive, and restore.
- Claude questions can answer themselves on a deadline (question-auto-answer): when every question of an `AskUserQuestion` call explicitly recommends an option in its label or description (`(Recommended)`, `I recommend this`, the observed typo `I recomend this`, or `My recommendation`; case/whitespace/punctuation tolerant, bounded to standalone, leading, or trailing annotations; negated and incidental mentions excluded), `recommendedAnswers` (`src/server/chat/contentBlocks.ts`) derives the answer and, if the saved wait is positive, `ChatSessionDriver.canUseTool` arms a server-side timer so the question survives with no browser open; the wait is the server-persisted `question_auto_answer_minutes` `app_settings` key (whole minutes 0–1440, default 5, 0 = off) behind `GET`/`PUT /api/settings/question-auto-answer`, read per question through the manager so a save never moves a pending deadline. The `question_request` event and the pending-question snapshot carry `autoAnswer` (what will be chosen and when) while the deadline stands: the card shows a countdown and **Wait for me**, and the form's first edit sends `chat-question-hold` so the timeout never overrides an unsubmitted answer. The deadline settles through the same `validateAnswers` path as a user — `request_resolved` with `decidedBy: 'timeout'` and the chosen labels, the transcript marker "Answered automatically", and a note in the tool result telling the agent the answer was automatic (a restart's replay shows only that note) — and every other path (a user answer, cancel, interrupt, kill, shutdown, a hold) clears the timer first; a held question waits for the user forever and a restart cancels the question without restoring any deadline. The auto approval policy still never answers questions.
- During an in-flight chat turn, a live activity row ends the transcript (`Waiting for model…` / `Thinking…` / `Writing <tool> input…` / `Running <tool>…` / `Retrying (a/m, status)…` plus a client-ticked elapsed timer). Derived server-side from protocol frames by the pure reducer in `src/server/chat/chatActivity.ts`, delivered on phase changes via the additive `chat-activity` message and `chat-snapshot.activity`; ephemeral (never a sequenced, persisted ChatEvent nor part of the session-list status) and hidden client-side while text streams, a request awaits the user, or the chat is archived.
- Background shells and Monitors a chat agent starts are visible and controllable: a per-session roster (pure reducer `src/server/chat/chatBackgroundTasks.ts`) joins each task to its `Bash`/`Monitor` tool call, rides the additive `chat-background-tasks` message and `chat-snapshot.backgroundTasks` (a full-set level signal, never sequenced events), and persists outcomes in a `chat-tasks/` sidecar (a row still running at restart recovers as stopped; kill deletes the file; archive keeps it). The tool row shows running with a ticking elapsed or the notification's one-line outcome (`✗` on failed), expands to the output tail — at most the last 8 KiB via the SDK's `get_task_output` while the query lives, else the recorded output file in the CLI's `tasks/` layout (`chat-task-output`); plain text with ANSI stripped, truncation noted, unavailable stated — and offers a per-task Stop (`chat-task-stop`), never in archived chats. Running tasks also list in the live strip beside workers. Tasks never change session status: a session whose turn ended reports `waiting` however much runs in the background, and a turn interrupt leaves them running — only process death settles them as stopped.
- Turns the agent starts on its own (a background task completed, a Monitor fired) stream into the transcript like user turns: the driver opens a turn on a `system/init` that arrives with no active turn (`session_state_changed` is `sdk_host_only` and never reaches SDK consumers), and `turn_started` carries a `trigger` — the buffered task notifications, or `resumed` when the cause is unknown. Replay maps task-notification transcript records to the same trigger line instead of a user bubble.
- Chat sessions show per-provider plan usage in a bar under the chat header (`UsageBar.tsx`): one thin meter per plan window (5-hour, 7-day, per-model weekly) with percent used and local reset time, plus a tick on the meter's track at the share of the window already elapsed (from the server-supplied `periodMs` — set in `usageWindowPeriods.ts` for known Claude kinds, and for provider quota rows from the row's own `unit`/`number` (observed codes only, `src/server/chat/zaiQuotaLimit.ts`) — and `resetsAt`; moved by a minute client clock, hidden once the reset passes; the row's hover text and the track's `aria-label` state used vs. elapsed and time left). `rate_limit_event` pushes and `/usage` reports are normalized by the SDK-free parsers in `src/server/chat/usageLimits.ts`, kept per provider in memory only (never persisted; absent after a restart until the next update) and shared by every session on any of that provider's profiles, delivered through `chat-snapshot.usage` and the additive `chat-usage` message (fanned out per subscribed profile of the provider — sibling sessions of one profile send one message — each named by the profile id plus additive `providerId`), and gap-filled once per provider by the SDK's experimental usage pull when nothing has arrived — claimed once per provider, so sibling profiles never double-pull. The SDK pull follows the host CLI login rather than the session's provider, so for a provider whose base URL's origin serves the Z.AI coding-plan quota endpoint (`/api/monitor/usage/quota/limit`, resolved against the origin so a path-prefixed model URL still finds it — undocumented; strict shape check in `src/server/chat/zaiUsage.ts`; only explicit auth codes count as a refusal, while a wrapped missing route reads as no endpoint) the server instead pulls plan usage with the provider's effective credentials in that slot (`source: 'provider'`), suppresses the host-login pull for it, and refreshes it every 10 minutes while a session on any of the provider's profiles has a started agent; a provider whose base URL host is `openrouter.ai` or a subdomain instead selects its own usage endpoint (`src/server/chat/openRouterUsage.ts`): the server pulls `/api/v1/key` at the base URL's origin with the session's effective token — each budget renders as one meter, a bare `limit` cap as one more, an uncapped key none — and, when the provider names `balanceKeyEnv`, `/api/v1/credits` with that server-side value as one more Credits meter (a 401/403 there drops only that meter and is logged once per key value, never with the key); a meter with nothing left reads limited, agent reports (`rate_limit_event` pushes, `/usage` reports) are not kept for it, no failure of these pulls enables the host-login pull, and a completed turn that carried `providerCostUsd` adds one pull 30 s later, at most one per provider per minute, beside the same 10-minute cadence while a session of the provider has a started agent; providers routed elsewhere (GLM gateways without the endpoint, MiMo, …) still show the logged-in claude.ai account's plan, and providers with no usage source (an API key, no login, neither endpoint) show no bar. Codex profiles report through the same bar: windows from `account/rateLimits/updated` pushes plus one boot fill read claimed once per home, normalized by `codexUsage.ts` into `codex:primary`/`codex:secondary` windows labeled by duration, keyed to the resolved home's provider id so every profile and session on one home shares the report and Claude profiles never see it.
- Chat sessions show CLI-style notices in a strip under the chat header (`NotificationStrip.tsx`), beside the usage bar, from two sources: account notices the server computes per profile (`src/server/chat/accountNotices.ts` mirrors the CLI's login-expiry rule from `.credentials.json` — shown while the refresh token expires within 3 days — checked on attach, agent start, and a 30-minute timer) and agent notices mapped from the SDK's `system`/`notification` frames (same-key replacement, `timeout_ms` expiry, cleared when the agent process ends: archive, kill, restart, shutdown, or an unexpected exit — the driver's in-place respawn then starts clean). Notices are ephemeral like activity: held in server memory, carried by `chat-snapshot.notifications` and the additive `chat-notifications` push, never persisted, sequenced, or replayed, and never part of the session-list status. Closing is per source: agent notices dismiss server-side (`chat-dismiss-notification`, every attached client); account notices hide in that browser tab only, keyed by text so a new day count shows them again.
- Chat header (`ChatHeader.tsx`, chat-transcript-layout D4): up to three wrapping rows. Identity/actions: a status dot and word plus the click-to-rename name (flexible space; the action group wraps below rather than squeezing it), then the **Team** button (opens the Team page for the chat's team on the tab last used for that team, Tasks the first time; present for archived chats and plain-directory teams), the **Auto-approve** switch, and the ⋯ session menu (Rename, Debug, Archive, Kill session — kill asks first; in the narrowest layout the Team button folds into the menu). Metadata: provider · profile · model · project (provider and profile one label when equal; project basename, full path on hover and to assistive technology), each field breaking long tokens, with the context meter at the trailing edge or on its own line. A task/paused row appears only when there is one. `useHeaderLayout` steps by the header's own width in chat-font ems (full ≥ 42em, icons ≥ 34em): the labelled Team button, then its icon form (accessible name `Team`), then folded into the menu with a percentage-only meter whose counts stay in its hover and accessible text.
- Chat transcript (`ChatMessages.tsx`, `ChatRow.tsx`, `transcriptLayout.ts`, chat-transcript-layout D1–D3): user, peer, and assistant messages are rows with an author/time metadata slot and a body slot inside `.chat-transcript`, a CSS inline-size container — at 34em or wider (in the chat font) metadata takes a 6.5em gutter beside the body, narrower it stacks above, so Debug, the navigator, the chat font, and nested worker transcripts reflow it without viewport media queries. Tool, notice, and activity rows align with the body column. Turns get a wide separator, author changes a dashed one; same-author continuations keep the time with the author for assistive technology only. Times are `<time>` elements with the full local date, time, and zone on hover (`chatTimeFormat.ts`, `ChatTime.tsx`); a local day separator precedes the first message of each new day. An event's `at` may be empty (undated replay records) and is read through `validTime` (`src/shared/chatTime.ts`) — an undated row shows no clock instead of a fabricated one. An assistant text block merges into the newest entry only when that entry is the last event with the same turn and message id, so text → tool → text in one SDK message stays in order, and a merged entry keeps its earliest valid time. Each message row carries a **Copy message** button on its time's line (`MessageCopyButton.tsx`, copy-chat-message-markdown D1–D4) that copies the event's own string — user `text`, assistant `text` (the Markdown source, per merged entry), peer `body` — never the rendered DOM; it is always laid out (`opacity: 0`, so revealing it shifts nothing), shown on row hover or focus-within and always under `hover: none`, and shows Copied or Copy failed for 2 s with a hidden status region. `copyTextExact` (`src/client/utils/copyText.ts`) uses the async Clipboard API only in a secure context and otherwise (plain-HTTP LAN/Tailscale addresses) or after a refusal sets `text/plain` on a one-shot `copy` event fired by `execCommand('copy')`, which keeps CR/CRLF intact; the older fire-and-forget `copyText` beside it is unchanged.
- Chat sessions can be archived (`archived_at` in `chat_sessions`; **Archive** in the chat header's session menu or the navigator row): archiving stops the agent but keeps the record, conversation, and protocol log; archived chats open read-only (no agent starts; Restore resumes the same conversation) and are exempt from the history lookback. Kill is still the only permanent removal.
- Boot restore (bounded-boot-restore D1–D4): persisted rows register from one async walk of `<CLAUDE_CONFIG_DIR>/projects` (`indexTranscripts`, `transcriptLocator.ts`, built at the first row with an SDK id so earlier rows still register synchronously), never a walk per row. A live row adopts its transcript's title and last cwd before `whenRestored()` resolves; an archived row registers at once with its stored name and path and catches up afterwards, one transcript at a time, through the live title and cwd paths (skipped once the row changed). Both read `scanTranscriptMeta` (`transcriptMeta.ts`): a chunked byte scan that decodes only title rows and parses cwd candidates newest first, answering exactly the full parse's `title`/`cwd` without holding the file — a several-hundred-megabyte transcript once took the event loop for minutes and gigabytes of memory. The start blocker's transcript-exists check (`TranscriptPathCache`) reuses a known existing path and walks again only on a miss; misses are never remembered.
- History loads (async-transcript-parsing D3/D4, bounded-history-capture D1–D2): a chat's replayed history is memoized once per process (`snapshotHistory`) by `ChatSessionManager.loadHistory`, which concurrent callers share and a kill during it never writes. Every driver start awaits it — attach, `send`, `start`, and the mailbox's `prepare` — so the first message to a chat with a huge history waits for the load instead of freezing the server. The synchronous `captureHistory` is only a guard in `getSnapshot` and `getHistoryPage`, whose callers await the load first; if it ever reads the file it logs `chat_history_sync_capture` naming the session, so a caller that skipped the await shows up. Both async replays stream the file through `readLines` (`lineReader.ts`: 1 MiB reads split on the newline byte, a partial line kept as copied pieces and joined once) into the line consumers behind the string parsers (`createTranscriptParser`, `createRolloutParser`), which give exactly the string parse's events and ids, so no whole-file string or line array is held; the parsed events themselves still are.
- Attach delivers the recent history window (chat-history-window): only the turns of the last 24 hours ending at the session's newest dated event, at least the newest turn, cut only on turn boundaries (`historyWindow.ts`, pure and SDK-free — live turns open with `turn_started`, replayed user/peer turns with their message). The snapshot carries `historyHasOlder` and `historyStartId`; pending requests, activity, rosters, notices and the live-tail `throughSequence` are delivered whole whatever their age, and archived chats window too. `chat-history-page { sessionId, beforeId, throughId? }` prepends the 24 hours before the oldest held turn (at least one turn across an empty gap), is answered to the asking connection only while it subscribes, replies `stale` for an unknown `beforeId` (the client re-attaches plain), never starts an agent, and lives in `CHAT_CONNECTION_TYPES`. The client folds the page alone (`applyChatEvents(emptyTranscript(), …)`, so its older live events never move `throughSequence`), drops ids already in `seen`, prepends, and sets in-memory `historyExpanded` — gone on reload, so a reopen recomputes the recent window; reconnects always send `historyFrom` from the held window start, reopens only when the user had expanded. A shown transcript never slides: reconnects keep what was shown and live events only append. The transcript's **Load earlier messages** control (`ChatMessages`, disabled while disconnected or loading, a start-of-conversation marker at the top of history) pins the first visible row across a prepend (`useHistoryAnchor`, with `overflow-anchor: none` on the scroller so the browser's anchoring does not compound, and one skipped bottom-stick), and a search reveal pages back once with `throughId` when its anchor is older than the window before falling back silently.
- Unsubmitted composer input is a per-session client-side draft (keyed by session id in `chatStore.drafts`): it survives switching chats and reconnects and returns after archive → restore, clears on submit, and is discarded on kill; it is never sent to the server or restored after a page reload.
- Chat search: the navigator filter bar's search box (`SessionSearchBox.tsx`; `[mod]+K` focuses it, ↑/↓ move through results, Enter opens, Escape clears, focus stays in the box) searches the content of every non-archived chat through read-only `GET /api/chat/search?q=` (2–200 characters after trimming, literal and case-insensitive; `src/server/routes/chatSearch.ts`). `src/server/chat/sessionSearch.ts` matches one session's events (user, peer, and assistant text, tool inputs and results, approvals, command output, notices, errors; streaming deltas skipped) and `sessionSearchWalker.ts` groups the response (up to 3 snippets per chat, 50 chats, 4 transcripts read at once). A loaded chat is searched from its memoized history plus live events; an unloaded one by a transient replay that is never memoized (`ChatSessionManager.searchableEvents`), so a search never starts an agent or pins history. While a query is searchable the results replace the navigator sections (project and host filters do not narrow them); choosing a snippet selects the chat and sets `chatStore.pendingReveal`, which `useRevealRow` resolves against transcript rows' `data-anchor-id` (the event id, or `tool:<callId>`), opening a collapsed tool card and flashing `.chat-reveal` for 2 s. Search state lives in `sessionSearchStore` and is never persisted.
- Navigator: live sessions sit in OpenSpec change/worktree sections; hibernating, history, and archived sessions collect in the docked `Archive` pane (newest first, collapsed until first expanded). `Remote` holds only live sessions on other hosts.
