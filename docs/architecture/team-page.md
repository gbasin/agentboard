# Team page

Messages view, the Team page shell and routing, the workspace read model, attention queue and morning summary, Members tab. Part of [the architecture reference](README.md).

- Messages view: the **Messages** tab of the Team page shows the team's mail feed, grouped by thread — one collapsible row per thread showing its newest message and whole-thread count, expanding in place to the loaded messages, with bodies clamped until expanded and **Expand all** / **Collapse all** acting on every loaded thread. It is read plus compose — the Mailbox tab keeps every delivery operation (Cancel, Retry, Discard, Hand off, Reload routing rules). One filterable, paged list holds delivered and pending mail newest first (keyset paging over `created_at` and rowid), narrowing by delivery state, priority, and human involvement; a host's own base filters (a task) survive alongside, and **Load more** follows the cursor. Rows name participants — a live session's name, the durable `team_session_directory` for a killed one (`Name (gone)`), `Human` for the human — with the raw id as expandable metadata and only a live or archived participant clickable. Opening a message shows its thread oldest first: each row's reply relation, current recipient, the task revision it carried at delivery, and its append-only `team_message_events` history. The human composer under both writes new mail addressed to one of the team's groups or sessions with an optional task, or a reply addressed to the parent's sender and inheriting that task without restating it. Urgent is explained where it is chosen: normal mail waits its turn; urgent mail interrupts a recipient agent's current turn once any pending approval resolves, or goes to the first idle member of a group. Refusals render inline and every control disables while disconnected. Neither an agent nor the human may start new mail to the human — only a reply in a human-started thread reaches them, settled on send with a toast. An uncertain hold keeps its history in the thread: Retry targets the same recipient with a possible-duplicate notice (the row marks it), or the human discards it. Task detail's Messages section draws the same rows with named participants and a link into each thread. The tab's search box sends `text` to the server, which matches it over the whole history (bodies and participant names), not only the loaded pages, with paging continuing inside the results. On the wire: one authoritative snapshot per open and reconnect (never on change), unfiltered change pushes the client filters itself, and a thread reply is replace-semantics, re-sent whole when its thread moves.
- Team page and side slot: team views (Strategy, Plans, Tasks, Messages, Mailbox, Members) mount only as tabs of the Team page (`TeamWorkspaceView`), never in a chat; the chat side slot hosts only the debug panel. The page is addressed by team key (`src/client/utils/teamKey.ts`: the main checkout of the discovered repository containing the path, else that path) — the same key the header Team button, the task chip, and the navigator's Team entry (one per discovered repository, never per worktree; selecting it never changes the session selection) compute. The URL hash `#/team/<key>/<tab>[/<sub>][/<id>]` names the tab, the Strategy sub-view, and the selected task or thread: tab and selection changes push history entries (Back and Forward move between them; navigating to the shown location pushes nothing), a reload restores the location, and a location naming an unknown repository or a missing task falls back to the tab's default view with a notice. Each tab keeps its search, filters, expansion, and collapsed sections per team in `teamWorkspaceStore` (memory only, never sent to the server, surviving tab switches, chat visits, and reconnects for as long as the browser tab is open); views follow workspace discovery for every chat, selected or not (`teamViewMigration.ts`, installed in App): a key inside a newly discovered repository moves to its main checkout, and a key never moves into another repository's team. Selecting a chat clears the team route (one history entry), and returning through the Team entry or Back restores the same team, tab, and selection.
- Team workspace read model: the Team page subscribes with `team-workspace-open`/`close` by team key and receives an authoritative `team-workspace-snapshot` on open and every reconnect, then `team-workspace` pushes that replace the whole read model (`teamWorkspaceDataStore`, applied by `protocol/teamWorkspaceMessages.ts`, re-keyed with the other team views). The server projects it in `src/server/team/workspaceRead.ts` — no tables of its own — and `workspaceConnections.ts` coalesces and diffs pushes per team. Task rows, attention items, member rows, and the morning summary all ride it; the workspace has no write path, every action navigates to the control that already owns it.
- Attention queue and morning summary: two collapsible bands (open state kept per team; attention starts open) sit above the Team page's tab strip on every tab. The queue lists pending approvals and questions, uncertain deliveries, staffing waits, pending acceptance, and results whose review requested fixes under **Needs you** (human-required) and **Waiting on agents**, each with cause, owner, impact, and a next-action button that opens its source: a task opens the Tasks tab, a message opens its Mailbox row expanded, a chat opens the chat, and a card opens the chat, or the plan it names when the decision card carries its `planId` (labelled **Open plan**). Pending acceptance is owned by whoever closes the task (`src/server/team/attentionAcceptance.ts`): a task created by a live agent session (present in the session records, not archived) lists it under agent-owned waits with that session as owner, while a human-created task, or one whose creator agent is archived or killed, stays human-required; acceptance rights are unchanged, so the human can still **Accept result** from the task. When the newest findings bound to the unaccepted outstanding result fail, the queue instead lists one agent-owned `fixes-requested` item owned by the result's submitter (next action **Wait for fixes**) and no pending acceptance. An unrecognized kind renders with its raw kind. Counts are derived from the replaced items; a toast fires once per `kind:sourceId` identity per client session when it first needs the human, the first snapshot of a team is a baseline that toasts nothing, and a replayed snapshot toasts nothing. The counts line is a polite status region, and when the focused item is resolved focus moves to the item now in its place (else the heading). The summary covers a rolling 24 hours in eleven buckets — completed results (each stating accepted or awaiting acceptance), capacity waits (labelled runtime-only: only waits the running server has observed), approvals, uncertain deliveries, finished turns without a result, and outbound sends; a finished turn with no submitted result by that session never counts as completed. Plan attention (plan-supervision D13, `src/server/team/planAttention.ts`) adds six kinds raised from each open plan's facts, gathered once per snapshot by `ChatSessionManager.planAttentionFacts` over the same supervision reads the monitor sweeps (`planAttentionFacts` is pure over them, derived at read time, nothing stored): a stopped change (`plan-stop`, human, **Retry or stop execution**; a re-stop after a retry is a new item by the row's generation), a stall (`plan-stall`, the plan's Lead role group else the human, **Unblock the holder**), an open decision card (`decision-question`, its addressed group else the human, **Answer the question**), an open fix or correction task (`plan-fix`, owner and next action by the task's fixStatus phase — the Lead role plans it, the human approves the revision and starts the approved execution, and both wait while it runs), an acceptance condition holding a change (`plan-condition`, human, **Resolve condition**), and the plan's newest failed promotion (`plan-promotion`, human, **Promote again** — never shown while its correction task is open; it returns when the correction closes). Every item links to its plan — `link.kind: 'plan'` with `planId`, plus `change` when scoped to one; a decision card's link is `card` carrying its `planId`, which opens the plan until the Plans view scrolls to the card — and clears when its cause clears; another team's plans never appear. The summary adds five durable plan buckets beside the six above — landings, stops, stall alerts, decisions, and overrides (`ChatSessionManager.planSummaryRows` over the execution, decision, and stall-alert stores' window queries) — none runtime-only, so they survive a restart; each item links to its plan, change-scoped where the row has one.
- Members tab: a read-only inspection of the team's groups — role description (never the prompt body), live members, task-creation right, effective workers grouped by provider with caps and live counts, approval policy (the resolved one, with its source: group file, team default, or built-in), member cap, routing strategy, limit policy, effort (the group level, then each per-model override: listed models in group order, then unlisted alphabetically), and warnings — naming the file that defines each group (both layers when both define it, the one in effect marked) and stating that prompt changes apply to future agent starts only. It has no control that edits a group or a running agent: its one team-level control (`TeamApprovalDefaultControl`, team-approval-default D7) sets the team's default approval for spawned members of groups without an `approval:` key — Manual or Auto-approve toggle buttons that send `team-workspace-approval-default-set`, show the snapshot's `approvalDefault` ("Not set" until first set; there is no clear), show a refusal inline, and are disabled while disconnected; the server publishes the team's workspace so every open view follows. Its other buttons open a member's chat.
