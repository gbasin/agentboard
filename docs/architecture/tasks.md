# Team tasks

Group settings, task records, rights and tools, task mail, staffing, member release, assignment and dispatch, revisions, results, checks, coverage, task controls, Task UI, workflow stage. Part of [the architecture reference](README.md).

- Team tasks (group settings): group frontmatter also takes `canCreateTasks: true|false` (default false: members cannot create tasks), `canCreatePlans: true|false` (default false: members cannot call `plan_create`; a strict boolean, an invalid value rejects the file like `canCreateTasks`; the human sets it, typically on the lead group), `canReportProcess: true|false` (default false: members cannot call `process_report_submit` or `process_proposal_link`; a strict boolean, an invalid value rejects the file; read at each call; the human sets it, typically on the lead group), `max: <n>` (live members of the group before worktree staffing stops spawning; default 1), `profile: <id>` (profile for spawned members; default profile when unset; profile routing generalizes it to `profiles`), `approval: manual|auto` (spawned members' policy; when absent the parsed group leaves it unset and the team default decides — see worktree staffing), `canManageMailbox: true|false` (default false; see the mailbox management bullet; an invalid value is a group warning and stays false), `effort: low|medium|high|xhigh|max` (reasoning effort every member's agent — spawned or human-created — launches with, as the SDK `effort` option/`--effort`; read at each agent start like the role prompt, so edits reach only later starts; unset = Claude Code settings decide; an invalid value is a group warning and is ignored; `CLAUDE_CODE_EFFORT_LEVEL` and a settings maximum still override or clamp it), `profileEffort: { <profile id>: <level> }` (single-line flow map; a member whose session profile has an entry launches at it instead of `effort`, resolved by `SessionTeams.effortFor(sessionId, groupId, profileId)` at each agent start with the record's `claudeProfileId`, or `default`; the file is never rejected — a non-map value is a warning and ignored whole, a bad profile id, a bad level, or a repeat of a profile already listed [the later entry is ignored, even when the first was invalid] is a warning and ignored alone, and an entry for a profile the group does not list warns but still applies; older servers ignore the key), `workers` (the new name of `profiles`, same list and capped-map forms; when set it wins and each old key — `profiles`, `profile` — is ignored with one warning, so `profile` beside `profiles` beside `workers` is no longer an error) and `modelEffort` (the new name of `profileEffort`, same values and warnings; when set it wins and `profileEffort` is ignored with a warning), both accepting a qualified `provider/model` key (one `/` between id-shaped parts) that groupCatalog resolves against the catalog — the provider's model's profile id when the provider holds it, reported and ignored like an unknown id otherwise, while the old keys keep their grammar and reject or drop a qualified name as today), `releaseOnTaskClose: true|false` (default true: a task's spawned members are released when it closes), `worktreeScoped: true|false` (default true: task mail is scoped to the task's worktree), and `canReleaseMembers: true|false` (default true: members may call `release_member`) — those three are strict booleans, invalid values reject the file like `canCreateTasks`. Spawn caps per team live only in the user-level `~/.kawai/teams.json` — `{ "maxSpawnedSessions": 5, "teams": { "/path/to/repo-or-worktree": { "maxSpawnedSessions": 8 } } }` — default 5, keys resolved to the repository's team, re-read when the file changes; a malformed file or value is logged and the default applies; project files can never set it. A member's worktree is the nearest enclosing directory holding `.git` (so a member in `<worktree>/src` still counts as in `<worktree>`); task targets must be the main checkout or a linked worktree listed by `git worktree list` and are stored as that root. Kawai never creates a worktree to satisfy a message.
- Team tasks are kawai-owned SQLite rows (`team_tasks`, `team_task_revisions`, `team_task_journal`; nullable `task_id` on `team_messages` and `chat_sessions`), scoped to one team: title, status (`open`/`active`/`blocked`/`done`/`cancelled`), creator (the human or an agent session), optional parent task, target worktree, and linked OpenSpec change. Direction and acceptance criteria live in numbered, immutable revisions (each publication adds one; earlier ones stay viewable); the journal is append-only. Tasks never belong to a session: archiving or killing the creator or any participant leaves the task, its revisions, and its journal in place, and participants are derived from the creator, associated sessions, task mail, and journal authors. Task status is kawai's own — it never rewrites an OpenSpec change's `tasks.md` checkboxes; a linked change's artifacts are only referenced as the authoritative direction.
- Task rights and tools: the human creates, drafts and publishes direction, notes, and sets any status (including reopening) from the UI; an agent creates only when its group's current file sets `canCreateTasks: true`, becoming the creator. Only the creator or the human amends direction/acceptance (refusals point to a note or a message to the creator); any team member appends journal notes and sets `active`/`blocked`; only the creator sets `done`/`cancelled`. The `kawai-team` server adds `task_create` (title, direction, optional acceptance, parent_id, worktree, openspec_change), `task_get` (bounded-log-reads-and-task-get: the task, every revision, assignment, publication, acknowledgement, and result whole — results sealed as below — and bounded windows read in one SQL transaction, oldest first with totals: the newest 50 journal entries, or `journal_limit` 1–200, paged older with `journal_before` and `bounds.journal.nextBefore`, the newest 100 subtasks, and the newest 50 messages; each journal entry is a preview of at most 2,000 stored bytes trimmed to a whole character, with `totalBytes`, `cut`, and `resumeOffsetBytes`, its text null when not valid UTF-8; the human's detail stays whole), `task_journal_read` (one entry losslessly: up to 8,192 stored bytes from `offset_bytes` as authoritative base64, the exact text when valid UTF-8, the total, and the next offset; entries are never rewritten), `task_note`, `task_update_status` (status, optional journaled note), `task_amend` (direction and/or acceptance, optional `rationale` and `notify`; publishes the next revision at once — agents have no drafts), `task_list` (bounded-task-list: compact rows — id, title, status, creator, parent, worktree, linked change, plan link, revision, timestamps, the outstanding assignment's target, role, claimant, and derived state, and the outstanding result's id, verdict, and acceptance, both from the derivation behind `TeamTaskSummary` — never direction, acceptance, instruction, or participants; `status` takes one status or `all`, and without it only `open`, `active`, and `blocked` are listed, the applied set returned as `statuses`; at most `limit` 1–200 (default 50) rows, newest first by `(created_at, rowid)`, paged with `before` and `bounds.nextBefore`, the filter, limit, anchor check, and count run in SQL in one read transaction with no revision join, `bounds.total` counting every match; a Codex thread started earlier keeps the old description and arguments but gets the compact, bounded default), `task_acknowledge` (task id and revision), and the result tools `task_submit_result`, `task_submit_findings`, and `task_handoff` (see the results bullet), all allowed without cards; identity is bound to the calling session. References are checked first: parents must be tasks of the same team, worktrees must be listed worktree roots, and linked changes must exist under `openspec/changes/` in the main checkout or the task's worktree. The system prompt's task note explains these rules and that a linked change's proposal, design, and tasks are authoritative. Delivered task mail records its header generation in the envelope metadata (`taskHeaderVersion`): new task mail carries 2, whose journal line names the paged `task_get` and `task_journal_read`; an absent version is the legacy generation 1, whose exact old line is kept, and the parser rebuilds the header only with the recorded generation's renderer, refusing an unknown version, one without a task, or a header that does not match it. The handlers are read per call, so every `task_get` is bounded, but a Codex thread keeps the tool catalogue it registered at `thread/start` (`thread/resume` sends no `dynamicTools`): a thread started before `task_journal_read` existed has neither the reader nor the paging arguments, while fresh Codex threads and every Claude spawn get the current catalogue. The task note (`TASK_JOURNAL_GUIDANCE`) tells every agent to check the bounds and, without the reader, to stop before conclusions needing omitted entries or bytes and ask for a fresh Codex chat — guidance, not enforcement; no chat is migrated.
- Worktree staffing: group mail whose task targets a worktree goes only to an idle member of that group whose resolved worktree is the target (other ordering rules unchanged); members elsewhere skip it — unless the receiving group's current file sets `worktreeScoped: false` (member-release), in which case any idle member of the group takes it wherever it runs and the mail never spawns; a missing group definition counts as scoped. After each dispatch pass, such mail that no idle matching member took triggers a spawn: a new chat of that group in the worktree root, with the group's `profile` and the resolved approval policy (team-approval-default, `resolveSpawnApproval` in `src/shared/spawnApproval.ts`: the group file's `approval:` key, else the team's default from `team_approval_defaults` — one row per team id, read uncached from SQLite at each spawn, so it applies with no browser connected — else `manual`; the group dispatch preview and the Members row call the same resolver and name its source: group file, team default, or built-in; the default is written only by the human's `team-workspace-approval-default-set` action over the chat WebSocket, never by a `kawai-team` tool, and changes only later spawns, never an existing chat), associated with the task and marked spawned (`chat_sessions.spawned`); the message becomes its first turn, delivered once. Spawning waits (and is re-evaluated whenever a member idles, archives, or is killed) while the group has `max` live members (every non-archived member counts, spawned or created by the human), the team has its `maxSpawnedSessions` live spawned sessions (only spawned ones count), or the worktree already has a live spawned member of any group (counted by resolved worktree, so one in a subdirectory still holds it). The cap check and the reservation (message state `spawning`, durable `team_spawns` row) are one transaction, with the reservation row inserted before the flip so the reserve notify's snapshot already sees it; a reserve that fails throws inside that transaction (rolling the insert back) and reaches the dispatcher's error path. A failed spawn drops the reservation, requeues the mail, and retries when its 30 s backoff ends — the dispatcher's timer is woken at that moment, so the retry needs no unrelated change. Startup drops leftover reservations and requeues their mail (never pushed, so receipt recovery is not involved). Queued task mail whose worktree no longer exists is dead-lettered `worktree-missing: <path>`; kawai never creates a worktree.
- Member release (team-member-release): when a task becomes `done` or `cancelled`, its live spawned members (never human-created sessions, and never members of a group whose current file sets `releaseOnTaskClose: false`) are marked pending release in the same close transaction — which also dead-letters the task's undelivered group mail to worktree-scoped groups as `task-closed` (direct mail and unscoped groups are untouched, at the close and for late arrivals in the dispatcher), so a done task never delivers its instruction late or spawns a fresh dev. A pending member is released — archived through the same path as a human archive, never killed — as soon as it is ready: idle, no pending approval or question, no live background worker, no running background task, no claimed or parked mail, no due direct mail (the one readiness definition, shared with the `release_member` tool and future hand-off flows; unavailable members count as ready). Evaluation runs in the dispatcher's `beginCycle` — awaited before the pass's diagnoses are collected, so a dead-lettered row is never reported as waiting and freed capacity serves waiting mail in the same pass. Pending releases are durable rows (`team_member_releases`), survive restart, and are cancelled by reopening the task or by any archive, kill, or human restore of the member (a restored member is never released again for the same close). A spawn still in flight at close gets its reserved message dead-lettered; the new session starts with no first turn, is marked at creation, and is released once idle. Every release appends a task-journal entry authored by kawai (`system`, rendered "Kawai", kept separate from `TaskActor` so the system is never a sender or creator) naming the session and why.
- `release_member` (member-release): a `kawai-team` tool, allowed without cards, that members of a group not setting `canReleaseMembers: false` (default permitted) can use to release one spawned member of their team immediately — archive only; no kill or restore tool exists. Refused with a specific reason — never deferred — for the caller itself, human-created sessions, other teams, archived or unknown sessions, and members that are busy, awaiting a request, running a background worker or background task, or holding mail. Success journals the release on the target's task; a settled member of an open task can be released to free its writer slot, leaving the task, its status, and its delivered mail untouched.
- Task assignment (`team_task_assignments`, plus nullable `team_tasks.request_key`) names who is responsible for a task, separately from the derived participant list: one append-only row per dispatch — target (a group, its role, or a session), the initial instruction verbatim, the dispatcher, the request key, the claim, and supersession. The state is never stored: it derives at read time from the instruction mail (queued while queued/spawning/awaiting-request, claimed, delivered, failed when the mail settles dead/cancelled/discarded with the reason shown, parked/forwarded/uncertain keeping their names, superseded from the row), and the claim is copied from the mail and cleared again on release or requeue. The outstanding assignment is the newest row that is neither superseded nor failed (delivered work stays outstanding until superseded; a failed instruction frees the task for reassignment) and rides `TeamTaskSummary`; the whole history rides the detail. Assigning changes no task status.
- Human dispatch: **Create and assign** and **Assign / send task** run through `AssignmentService` as the human for the session's team, committing the assignment row and its instruction mail in one SQLite transaction (a refusal writes nothing; an accepted dispatch always has its mail). The instruction is an ordinary `team_messages` row whose sender is the human on the actor model `team-message-threads` ships (`from_kind: 'human'`, no sender session, origin = the team's main checkout root) — so claims, receipts, routing, worktree filtering, and spawning all apply unchanged, and an agent's reply in the dispatched thread reaches the human exactly as that change specifies (settled on send, toast, thread row; the task journal stays a complementary record). Create and dispatch carry a stable client request key, unique per team on both tables: a reconnect resend, a double click, or a replay of the same key and payload returns the prior outcome and never duplicates a task or an instruction; the same key with a different payload is refused naming the differing field, and the armed create key is re-minted when the form changed after a lost result. When creation commits but dispatch is refused, the task stays, every form field remains, and **Retry assignment** reuses the existing task and key (an edited target or instruction re-keys: the refused dispatch wrote nothing).
- Reassignment is an explicit handoff: dispatching onto an outstanding assignment requires the human to choose **notify** or **stop**. **Stop** supersedes it and cancels the old instruction only while queued or awaiting-request (a `spawning` reservation is left to staffing's lifecycle; claimed or delivered work is never auto-cancelled; nobody is killed or archived). **Notify** supersedes it and sends the previous claimed agent — when one exists — a fixed normal-priority direct note ("Task … was reassigned to …; your work is not cancelled — report status with a journal note if still relevant."), degrading to a plain supersede without a claim. All reassignment writes commit with the dispatch. A read-only preview (`team-task-preview`) answers the target worktree, role, effective profile (the session's, or the first profile a spawn could use), approval policy, staffing availability, and — warned, never blocked — a session target outside the task's worktree; dispatch revalidates everything. Dispatch never creates a worktree: the worktree pickers link into the existing creation flow and refresh on return.
- Task revision publication (task-revision-publication): the human edits a task's direction as a **draft** (`team_task_drafts`: one per task, direction, acceptance, rationale, and the published revision it is based on) that publishes nothing — no revision, no `updated_at`, no mail, no task-change event (its own listener refreshes only the human's view), never in `task_get` or a delivered header (`HumanTaskDetail` is the only detail type with a `draft`). **Publish revision N** / **Publish and notify** record the next immutable revision with its rationale, author, command key, and notify flag (nullable columns on `team_task_revisions`, old rows read as "published before notifications"): one transaction resolves the key first (a same-payload replay returns the prior revision; a different payload is refused naming the field), then refuses a stale base naming the newer revision (the draft stays; **Rebase onto revision M** moves only its base), inserts N+1, and drops the draft when the publication came from it (`fromDraft`, set whenever a draft exists — edits beyond the saved text still replace the one draft) — the partial unique `(task_id, request_key)` is the arbiter, and a request that loses a same-key race resolves as the replay. `TaskStore.changed` fires once per new revision, never for a replay, refusal, or draft. Notices (`taskNotices.ts`, `team_task_notifications`) are written in that same transaction: one direct, normal-priority task message tagged `task-revision` with `revision_notice` (`revisionNotice` in the envelope) to the outstanding assignment's current claimant (following forwarded work to its successor), never group mail — an unclaimed group assignment needs none, its instruction is built with the newest revision at push; a killed claimant's notice is dead-lettered while the revision stands, an archived one is restored after commit. **Notify** / **Retry notification** (`team-task-notify`) is one keyed command that sends each holder lacking the revision (not delivered it or newer, no pending or uncertain notice) one notice and never writes a revision; its replay sends nothing. The publication detail derives per holder, never stored and never merged: notice state (Not notified, Queued, Delivered, Failed with reason, Uncertain — linked to the Mailbox, whose Retry/Discard resolves it), the delivered revision (highest `task_revision` of task mail delivered to it), and the acknowledged revision. Agents call `task_acknowledge` (`team_task_acknowledgements`, keyed by session; unpublished revisions and other teams refused, repeats no-ops) once they work from a revision; only the current claimant's acknowledgement shows, so a reassigned, requeued, or forwarded holder starts unacknowledged, earlier rows staying in the history. Delivered rows keep the revision they carried. The revision-published contract is the `team_task_revisions` row plus `team_tasks.revision`, compared at read time; `TaskService.onRevisionPublished` is an optional after-commit announcement (never on a replay, draft, notice, retry, or acknowledgement) that nothing depends on. The UI's publish and notify keys live in the task store per armed slot — reused while the payload is unchanged (double click, reconnect resend; Notify and Retry notification are distinct payloads, so a Retry after a lost Notify result is a new command), retired on success.
- Task results and handoffs (task-results-handoffs): a result is a `team_task_results` row — summary, commit and/or diff, the worktree (the task's, else the submitter's), test outcomes shown labeled **(claimed)** and never verified, limitations, the submitter, and the task revision pinned at submission; a newer result supersedes the outstanding one (both stay readable). **Needs re-evaluation** is derived at read time (pinned revision older than the task's current one), never stored. Agents submit with `task_submit_result` (a new result per call) and review/QA findings with `task_submit_findings` (`team_task_findings`), bound to the exact result examined — never transferred to a later one — and recording the handoff they answer when the caller holds it. Handoffs (**Request review**, **Request QA**, **Return for fixes**; agent `task_handoff`, whose optional `target_kind: group|session` with `target` names the recipient — a group, the default and always the reading when `target_kind` is omitted even for a session-shaped id, or one named same-team session, which dispatch validates like any assignment (unknown, killed, archived, other-team, or blank refused before anything is written) and hands ordinary direct task mail to without spawning, restoring, or moving anyone) are ordinary task-assignment dispatches whose row also carries `handoff_kind`, `result_id`, and `expected_response` — all part of the request key's payload identity — with an instruction naming the result and commit; every handoff supersedes the outstanding assignment as the next stage through reassignment's **stop** branch — no notify/stop choice, no reassignment note, a journal line naming the handoff kind, and the predecessor's instruction cancelled only while queued or awaiting a request (claimed or delivered work is never touched), so a superseded stage never delivers later — and the request-key replay and an agent's retry, which returns the standing equivalent handoff instead of dispatching twice — the notice naming its recipient kind and id and, when the retry names another recipient, both with the statement that no reassignment occurred — both resolve before supersession, so neither supersedes its own handoff. Acceptance (**Accept result** / `team-task-accept-result`) checks closing rights first with the exact `done` rule (the human, or the creator agent) — a contributor's accept writes nothing — shows the acceptance criteria and open child tasks, and requires a stated reason when the result needs re-evaluation or children are open; the acceptance, its journal entry, and `done` commit in one transaction. Acceptance is per task: a finished child never closes its parent. **Release worktree and hand off** (human only, `team-task-release`) archives the task's live spawned members through member release's readiness, archive, and journal paths, then dispatches the review; any member not ready (awaiting an approval or answer, busy, running a worker, holding mail) refuses the whole action with its name and reason, archiving and dispatching nothing. The confirmation lists who is archived and, separately, other live sessions in the worktree that stay and can still edit it. A review handoff of the outstanding result already queued behind the occupied worktree is the one that proceeds — release never dispatches a second.
- Result checks (independent-verification): every submitted result is checked by Kawai and never gated by it. The pending row (`team_task_result_checks`; the partial unique index holds one pending row per result, `UNIQUE(result_id, seq)` the history) commits in the result's own transaction, and the check runs only after that commit — one flight at a time per team (`ResultCheckService`, `src/server/verification/`), every git call read-only (`--no-optional-locks status`, `merge-tree --write-tree` at most), under a 120 s budget that records the check `unavailable` with its reason when a call does not answer. The versioned facts (≤64 KB) cover the commit's resolution, the worktree's HEAD relation and cleanliness, the tree's recorded full-check pass under the commit's `.bun-version`, the merge into `refs/remotes/origin/HEAD` as last fetched (conflicts, commits behind), and each other open task's listed worktree head (conflicts and shared files, 30 heads newest first, 20 files per list). Nothing downstream consults a verdict: no execution, landing, supervision, decision, dispatch, staffing, or routing module imports `verification/` (structural test), and a settled check only refreshes readers. Recheck (agent `task_check_result`, human `team-task-recheck`) records a new check beside the earlier ones — a request while one is pending returns it — and task detail carries each result's newest check plus the earlier count ("Checked by Kawai", informational; the test list stays claimed). Checks left pending by a stop run once after startup.
- Coverage maps and the blind-first seal (independent-verification): a result may carry a **coverage map** — which clause of the direction it believes covered by which test — as clauses of citations `` `path` › `title` `` (≤200 clauses × ≤10 citations each, clause text ≤500 chars), validated whole on `task_submit_result` (a malformed map refuses the submit naming the clause index, and nothing is written) and append-only afterward per reader through `task_submit_coverage` (agents only, the result must belong to the task; the newest row per author session is the one shown; the submitter's own map rides the result row, sealed like every other session's). Kawai's check resolves each citation at the result's commit — it reads the file from the commit's tree, matches the literal test title, and classifies the run from the recorded pass's test list: found and passed reads `ran-passed`, skipped `not-run`, absent from the run `not-in-run`, found without any test list `run-unknown`, file or title missing `not-found`; a result with no commit to resolve (diff-only, or an unresolvable sha) reads every citation `unresolved` — and the outcomes join the map positionally; when facts crowd the 64 KB cap the outcomes drop whole, never truncated positionally. The clause's status derives by first match: no tests declared-uncovered, any outcome unresolved, all good covered, all run-unknown covered-run-unknown, both good and bad partly-covered, else not-covered (good = ran-passed or run-unknown). The **blind-first seal** is an information-flow projection on read results (`TaskResultService.sealResults`, behind both `task_get`'s `applySeal` and `task_submit_coverage`'s return — recording a map through the tool never hands back more than the reader may see), not a store state: a session holding the task's outstanding review handoff for a result — the session target or the claimant — sees every coverage map withheld as `{withheld: true, clauses: n}` (its own map's existence decides, never its content) until it records its own map for that result; the human and every unsealed reader see maps whole, each reviewer's map beside the comparison's differences (`onlySubmitter`, `onlyReviewer`, `differingCitations`, `uncoveredDisputes` — empty kinds omitted, "the two maps agree" when none). The pure model (grammar, limits, six outcomes, status table, seal, comparison) lives in `src/shared/coverageMaps.ts`; `handoffInstruction` never renders a map; maps never gate anything — no review, handoff, or acceptance consults them. The client renders the claimed map with only the citation outcomes labeled "(checked by Kawai)", the withheld stub, reviewer maps, and the comparison (`CoverageMapView.tsx`).
- Human task controls go over the chat WebSocket, addressed by the team's directory rather than a chat (`teamPath`: a repository's main checkout, or a chat's directory outside any discovered repository; the server resolves it and refuses, as `unknown-team: <path>`, any path that is not a discovered repository, one of its worktrees, or the team of a non-killed chat — the same addressing every human mailbox, messages, and strategy view uses, and replies echo it beside `teamId`) (`team-tasks-open`/`close` for the list, `team-task-open`/`close` for a detail; authoritative `team-tasks-snapshot`/`team-task-detail` pushes on every task or task-mail change; another team's task is refused). The human creates tasks (with optional parent, worktree, and linked change) and — regardless of who created a task, including a killed agent — drafts and publishes its direction, sends revision notices, appends notes, and sets any status including reopening (`team-task-create`/`draft`/`publish`/`notify`/`note`/`status`, and for results `team-task-accept-result`/`handoff`/`release`, answered by `team-task-result`, which carries the published revision and whether a keyed command replayed, which also returns an assignment after `team-task-assign`); `team-task-preview` and `team-task-targets` answer the dispatch preview and the pickers' team-scoped worktrees (with branches) and OpenSpec changes (with locations, narrowed to the chosen worktree's validating roots). Sessions carry `taskId`/`taskTitle` and `spawned`; a spawned session in `permission` status (a pending approval or question) needs attention: its navigator row is flagged and a toast fires on the transition, beside the usual permission sound, whether or not a task view is open. Auto-spawned members use their group's `approval` policy (manual unless the group sets `approval: auto`).
- Task UI: the **Tasks** tab of the Team page (reached through the chat header's **Team** button or the navigator's Team entry; the chat's task chip opens this tab with that task) shows the team's tasks full-width. The list groups subtasks under their parents (a collapsed parent states its count) and searches over title and current direction with marked matches — a matching subtask keeps its ancestors and shows even under a parent collapsed earlier, and a match deep in the direction shows as a snippet around it; each task shows its title, status, creator (`Human`, a session name, or `<id> (gone)` once killed), participants, its direction line, and its assignment (target and state, or Unassigned); **New task** takes a title, direction, optional acceptance criteria, parent task, a target worktree and linked OpenSpec change chosen from searchable pickers (typing stays available and validates on the server the same way; the worktree picker links into the worktree-creation flow and refreshes on return), and an optional assignment — group or session plus the initial instruction, with the note that group dispatch selects one eligible member, an on-demand dispatch preview (worktree, role, profile, approval, staffing), and **Create task** / **Create and assign** buttons armed with one stable request key; a refused dispatch keeps every field and offers **Retry assignment**. A task's detail shows its current direction and acceptance plus the results with acceptance and handoffs, release-and-hand-off, the publication detail, the outstanding assignment with its target, role, state, and claimed agent, the assignment history, the direction draft editor, the journal, subtasks, and the task's messages — each section (Assignment, Direction, Acceptance, Revision history, Results, Release, Publications, Status, Journal, Subtasks, Messages) collapses on its own and stays collapsed across tasks; **Assign / send task** (over an outstanding assignment the **notify**/**stop** choice is required first), **Mark <status>**, and **Reopen** for closed tasks; every control disables while disconnected and refusals show inline. A chat working on a task names it in the header (`Task …` or `Spawned for task …`; click opens the Team page's Tasks tab with that task). Peer-message rows show a collapsible task summary (title, status, revision, worktree, linked change, direction, acceptance, latest journal), and a revision notice adds "Revision N published" with its rationale. In the navigator, chat rows carry `spawned`, task-title, and `needs attention` badges (the last for a spawned session awaiting an approval or answer), under the worktree their current path belongs to.
- Task workflow stage: Tasks rows show the task's status and, beside it, a workflow stage projected by `src/shared/teamTaskStage.ts` — an outstanding review/QA/fix handoff (In review, Ready for QA, Fixes requested, even while queued), else an unaccepted outstanding result whose newest findings fail (`TeamTaskSummary.outstandingResult.reviewVerdict`; Fixes requested, next action **Wait for fixes**), else any other unaccepted outstanding result (Awaiting acceptance), else Implementing or Unstarted from the assignment; closed tasks show none, and a finished turn never moves it. Rows also name the accountable session or requested role, worktree, current waiting reason, and next action, plus badges **Needs re-evaluation** and **Awaiting acknowledgement** (delivered and acknowledged revisions kept apart: "Delivered rev 2 · Acknowledged rev 1").
