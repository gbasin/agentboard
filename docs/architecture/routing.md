# Routing and limits

Profile routing, routing rules, group-mail dispatch, worker choice, rate/credit limits and cooldowns, context exhaustion. Part of [the architecture reference](README.md).

- Profile routing (group settings): `profiles: [a, b]` or `{ a: 2, b: 1 }` (single-line flow values; order = preference; the map caps live group members per profile — every non-archived member counts, user-created or spawned, busy or parked, plus pending spawns — and `max` defaults to the caps' sum; a single `profile` still works; unknown ids are warned and dropped), `strategy: first-available|profile-order` (built-in routing; both skip cooling profiles; members always beat spawning), and `onLimit: { parkIfResetWithin: 3h, otherwise: forward|release, forwardTo: <group or session> }` (invalid values are warnings, defaults apply). The groups route returns these warnings and per-profile caps with live counts; the New Session dialog warns (never refuses) when a profile's cap is reached. See `docs/routing/README.md`.
- Routing rules: `~/.kawai/routing/<group>.ts` only (never project files) default-exports `{ route, onLimit?, env?, timeoutMs? }`, typed by `kawai-routing.d.ts` that kawai publishes beside them from `src/shared/routing.ts` (type-only, so it is copied verbatim). Each rule runs in a Bun Worker: a bootstrap Worker with `env: {}` reads its declared `env`, then the serving Worker gets exactly those variables; calls time out (default 3 s, max 10 s; restarted after 3 consecutive timeouts). Rules load at server start and on **Reload routing rules** (`team-mailbox-reload-rules` → `team-mailbox-rules-result`; every mailbox snapshot carries `routing: { rules, decisions }`); file edits alone never apply. `src/server/team/routing/`: `ruleLoader.ts`/`ruleHost.ts`/`ruleWorker.ts` (runtime), `candidates.ts` + `builtin.ts` (pure), `router.ts` (decisions, holds, per-group log).
- Group mail is routed one message at a time (`dispatcher.ts`): per pass urgent direct, urgent group, normal direct, normal group; groups route concurrently, one decision at a time within a group. The router sees idle, available, request-free, non-parked members in the task's worktree plus spawn slots staffing allows (`staffing.spawnContext`/`spawnFor`, whose reservation transaction re-counts per-profile caps; `team_spawns.profile_id`). Rules see metadata (priority, sender group, tags, worktree, task id; never the body), candidates (cooling ones included), caps/live counts, and per-profile usage (with `source`: push/report/pull) and limit events. Throws, timeouts, and unknown picks fall back to the built-in strategy; a stale pick is re-routed once, then built-in; holds wait for their retry time or a candidate change. Urgent direct mail never consults a rule.
- Worker choice (dispatch-worker-choice): group mail may name a `worker` — a provider id or `provider/model` (a bare model key normalizes to `provider/model`; an ambiguous bare id, an unknown one, or one outside the group's workers is refused, and a session target with a worker is refused writing nothing) — on `send_message`, `schedule_message`, and `task_handoff` (never `reply`), stored canonical as `worker_choice` on `team_messages` and `team_task_assignments` (`workerChoice`; null reads as no choice). Each pass resolves it against the group's workers and intersects it with the role's `allowed_profiles`, keeping the role's order, through the one pure check `workerEligibility.ts` that the dispatcher, staffing, and the dispatch preview share: only chosen members and spawn slots are candidates, a rule pick outside them falls back to the built-in pick, and a cooling or capped choice waits — never routed elsewhere — with the `worker-choice` waiting reason (retrying at the cooldown end); rules see it as `RouteContext.message.worker`, and a limit forward drops it while still excluding the limited worker. `team_capacity { group? }` (card-free, bound to the caller's team) answers each group's max, live count, strategy, and workers in preference order (model, provider, cap, live members with pending spawns, cooldown end) plus each listed provider's usage, cooldown, and `sharesLoginWith` — ids, counts, usage, and times only, never a credential, env value, config dir, or URL. The human dispatches with an optional `worker` on `team-task-assign` (Create and assign's assign leg; `team-task-create` takes none), `team-task-handoff`, and `team-task-release` (validated before anyone is archived; a standing review counts only with the same choice, else it is superseded — a claimed one stays live beside the new review), each part of the request key's payload (same key, other worker refused naming `worker`; a normalized-equal one replays); `team-task-preview { worker? }` reports the choice, its models, the effective profile, and staffing through the same check, warning — never refusing — with the cooldown end when the choice cools. The Tasks forms (New task, Assign / send task, the handoff form, the release dialog) show a worker picker for group targets only, its workers grouped by provider with usage and cooldown from `team-task-capacity` — the same `TeamCapacity` read the tool answers — and the chosen worker inside each armed key.
- Limits: the driver reports rate-limit/billing/overload errors and any 429 (`limitSignals.ts`: `api_retry` = non-final, failed assistant message = final, reset from a rejected `rate_limit_event`, else from a zone-less `reset at <date time>` in the error text read in the profile's `limitResetTimeZone` — IANA zone or `±HH:MM`; the shipped `glm` uses `Asia/Shanghai`) into `profile_limit_events` (pruned after 15 days for process metrics; routing reads only the last 24 h). Cooldown (`limitEvents.ts` `cooldownFor`, providers-and-workers D8) is computed per window group: the latest final event of each window (`limit_window` from the rejected `rate_limit_event`; null counts as one group) sets its end — its reset, else +1 h — and the profile cools until the latest end still ahead, over its own events whatever their provider plus its provider's provider-scoped events, so the shipped `glm` and `glm-flash` of `zai` cool together from one event; `MODEL_SCOPED_WINDOWS` (`seven_day_opus`, `seven_day_sonnet`) cools one profile alone, and rows recorded before providers (migration 12) cool only their own profile. Every cooldown reader goes through `cooldownFor` (router states, recipient snapshots, dispatcher rows, the spawn preview, the recovery notes), and the wording names the provider when its cooldown decided (`waitingLabels.ts`, the urgent refusal, the decision log, the hand-off note). When the turn handling a delivered message ends after a final limit (`limitOutcomes.ts`), the message is parked (state `parked`, resume mail scheduled at the reset, holder paused — `Session.parked` badge/header — and skipped by group routing; once due, its resume goes before the holder's other normal direct mail; a successful human or resume turn unparks; released after 3 parks), released (back to the group queue; direct mail to the holder's group), or forwarded (new message with a `handoff` package: progress digest, last error, claim commit from `git rev-parse HEAD` at claim, inspect-first instruction; `excluded_profile` keeps it off the limited profile and, while that provider cools, off its other models (buildCandidates hard-filters them; a Hand off to such a session is refused); `team_handoff_notes` tells the original agent who took it once its profile recovers). The rule's `onLimit`, else group `onLimit`, decides. A human-created session (`spawned` false) whose human turn, or agent-started turn holding no other work, ends after a final limit with a reset ahead gets one scheduled direct `limit-resume` message to itself at the reset (`limitResume.ts` decision, `limitResumeMail.ts` writes; limit-resume-unheld-sessions): it shows as paused (`parkedState` falls back to `pendingLimitResume`), names the background agents that failed on a limit (`isLimitFailure` over roster pushes, deduplicated by task id), is superseded in one transaction by a later reset or a newly lost worker, is cancelled by a successful human turn or archive, is never resolved as work (no park, release, or forward), and stops after 3 consecutive limited attempts until a successful human or resume turn; credit limits and spawned sessions get none. The human can **Hand off** parked work (`team-mailbox-hand-off`). Urgent direct mail (send or reply) to an agent whose profile is cooling is refused with the cooldown end, naming the provider when its cooldown decided. Credit limits (openrouter-provider D7/D8): an HTTP 402 — from the class or the `API Error: 402` text, whatever the class — is a final limit with `window: 'credit'` and no reset; it cools at most +1 h, ending earlier through `LimitEventStore.reportRemainingCredit` (in memory, fed by provider usage pulls; nothing calls it until the OpenRouter usage adapter) once a pull after the event exceeds the lowest earlier post-event pull — readings from before the event are ignored and the first post-event pull only sets the baseline, and tracking starts when the process records the event, so an event loaded after a restart ends at its hour whatever later pulls report; `EffectiveCooldown.credit` marks a credit end. Credit-limited work is never parked: `resolveLimit` takes `otherwise` (a rule's `park` too), and an agent-started turn's credit limit leaves its work; the `profile-cooling`/`all-profiles-cooling` constraints carry `credit` and read "out of credit … at the latest", as does the urgent refusal. Codex limit classes (`codexErrorInfo`) on a failed turn: `usageLimitExceeded`/`rateLimitExceeded`/`serverOverloaded` are final login-scoped signals via `codexLimits.ts` recorded once with the home's provider id, while `sessionBudgetExceeded` records for its profile alone with no provider; a retrying `error` notification is non-final; everything else records nothing; a Codex 402 is never a credit limit; the reset is the latest `resetsAt` among the exhausted windows, used percent at 100.
- Context exhaustion (chat-context-exhaustion): a turn succeeded only when `turnSucceeded` (`src/shared/chat.ts`) holds — subtype `success` and no `is_error` — so the CLI's `Prompt is too long` refusal (a success result with `is_error`) is a failed turn for mail outcomes, turn ends, the morning summary, and turn usage; `turn_completed` carries `isError` and `terminalReason`, the driver's error row names the reason (`resultErrorText`), and replay maps API-error replies to error rows. A failed turn whose terminal reason is in `EXHAUSTING_REASONS` (`prompt_too_long`, `blocking_limit`, `rapid_refill_breaker`) flags the session (`chat_sessions.context_exhausted_at`/`_reason`, `Session.contextExhausted`; a repeat keeps the first flag, one episode per flag) until a `compacted` notice or a successful turn clears it; the navigator shows a **Context exhausted** badge and the header's task row "Context exhausted (<reason>) · Run /compact or start a new session". A flagged session takes no mail: direct mail, replies, and session-target task dispatches (`AssignmentService`, flag read after its last await) to it are refused naming the flag (nothing queued, an archived one never restored), group routing skips it (still counted toward caps; waiting reason "context exhausted"), and a Retry of its session-addressed `context-exhausted` dead letter is refused while it stays flagged. The turn's mail takes the exhaustion outcome (`contextExhaustion.ts`, one transaction, never park, forward, or cooldown): the handled message is dead-lettered `context-exhausted` (Mailbox label "The recipient's context was exhausted; the message was not processed"), parked work returns to its group (resume cancelled; dead-lettered without a group), queued direct mail to it is dead-lettered, and a spawned member with a task is marked for release at once (reason `context-exhausted`, even under `releaseOnTaskClose: false`; cancelled when the flag clears). After commit `ExhaustionNotes` records the episode once in `team_exhaustion_episodes` (key: session and flag time) and sends one normal-priority direct note tagged `context-exhausted`, self-sent, to the dropped message's assignment's dispatcher, else the outstanding assignment's, else the task's creator — never the human or a killed, archived, or flagged session, rechecked after the HEAD read (an ineligible one leaves the episode with no recipient, so the item stays with the human) — naming the dropped message, progress digest, claim commit, HEAD, the acknowledgement state, and each group provider's usage and cooldown. Each open episode is a `context-exhausted` attention item (`workspaceExhaustion.ts`, id `<session>:<flaggedAt>`): owned by the note's recipient (waiting on agents), else the human (needs you), opening the dropped message's Mailbox row or else the chat, and resolved at read time by a newer dispatch on the task, the task closing, the dropped message retried or discarded, the flag clearing, or the kill. Kawai never compacts or starts a turn in a flagged session.
